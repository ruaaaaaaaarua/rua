# GLM 批量分析速度优先设计

**状态：** 用户已确认，直接实现  
**日期：** 2026-09-11

## 目标

压缩图片识别完成后的 GLM 批量解题与诊断时延，不改变题目识别、答案判定、学习证据和逐题恢复路径。

最近一次十题分析的本地调用记录显示：批量解题耗时 72.4 秒、生成 6,764 tokens；批量诊断耗时 50.8 秒，输入 12,189 tokens、生成 5,337 tokens。两次调用串行，因此后半段约 123 秒。

## 已确认方案

仅对 `solve_batch` 与 `diagnose_batch` 的 GLM 请求采用速度优先策略：

1. 不依赖设置页开关。当前 `glm-5.3-flash` 始终思考且拒绝 `thinking.disabled`，因此批量调用固定传支持的最低 `reasoning_effort: "low"`；其它支持关闭思考的模型传 `thinking: {"type":"disabled"}`。其他 GLM 任务和逐题恢复调用保持原设置。
2. 批量调用上限固定为 4,096 completion tokens；普通/逐题调用仍使用现有默认上限。
3. 解题批量提示要求答案依据为一至两句，不生成展开推导。
4. 诊断批量提示不要求无页面消费者的 `explanation` 字段；知识点、诊断、区分和提示均保持短句。
5. 诊断时每题只传最相关的前三条历史知识记录，而不是最多十二条。题干、选项、学生作答、独立解答和参考资料仍完整保留。

## 兼容与失败处理

批量模型仍必须通过既有 Pydantic Schema 和选项答案校验。若 4,096 token 上限导致批量结果不完整或不合法，当前的逐题 `solve` / `diagnose` 回退保持不变；该回退不强制关闭思考，也不改变其 token 上限，以保留恢复质量。

## 验收

- GLM 5.3 批量请求含 `reasoning_effort: low` 和 4,096 token 上限；其它兼容模型的批量请求含禁用思考和相同上限。
- 批量解题提示明确限制解释长度；批量诊断提示不再请求 `explanation`。
- 每个诊断项传入的 `history` 最多三条。
- 批量成功、部分结果逐题回退、答案/证据边界的现有测试均通过。
- 使用同一张十题图复测并记录两次 GLM 调用和总后续耗时；真实模型时延作为观测值，不承诺固定秒数。
