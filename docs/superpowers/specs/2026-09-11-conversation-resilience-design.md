# 对话区与整页分析韧性设计

## 目标

让整页学习界面把主要可视空间留给结果总览，并让批量诊断偶发失败不再把一次整页处理退化为“逐题重新解题 + 逐题诊断”的分钟级串行流程。模型配置应能为 DeepSeek 与 GLM 分别设置并发上限，实际默认值只在真实测量后调整。

## 范围与顺序

1. 聊天区默认紧凑、可拖拽调整高度；解释与自由追问可映射到 DeepSeek，生成与复核继续按现有任务映射保留 GLM。
2. 批量诊断失败时，重试一次批量诊断；仍失败时复用成功的批量解题结果，仅逐题诊断。缺失批量解题结果的题才逐题解题。
3. 将并发限制改为模型配置级别，并对 GLM 与 DeepSeek 作受控实测；对同一凭据共享 token 窗口，不让两个不同供应商彼此限速。

## 对话区交互

- 初始高度为 240px，而不是由内容自然膨胀到页面近半。
- 顶部有一条可拖拽分隔条；向上拖动扩大对话区，向下拖动缩小。
- 最小高度为 156px；最大值同时保留至少 240px 给总览区。高度使用 `localStorage` 在同一浏览器恢复。
- 分隔条是可聚焦的 `role=separator`，键盘上下方向键以 24px 调整，方便不用鼠标的操作。
- 现有“高级任务覆盖”保持五类任务的明确映射。只要本机添加 DeepSeek profile，即可把 `chat` 选择为它；`generate` 和 `verify` 不自动迁移，维持 GLM。

## 批量诊断降级

1. 批量解题成功后保存每个可用的 `solution`。
2. 对完整诊断输入调用批量诊断；若返回安全的 provider 错误，自动再调用一次。
3. 两次批量诊断都失败时，对有 `solution` 的题只调用逐题 `diagnose`，绝不再调用 `solve`。
4. 对批量解题缺失的题，才调用逐题 `solve`，随后调用 `diagnose`。
5. 成功的批量结果继续直接合并；局部缺失的结果仅针对缺失项降级。

这样保留正确性边界：所有分析仍须同时有独立答案与诊断，不能把诊断失败的题误标为已确认。

## 失败可观测性

每次模型调用记录新增安全的 `error_kind`，例如 `response_schema`、`rate_limited`、`network`、`server_error`。不保存原始响应、prompt 或密钥。页面现有通用错误文案不暴露供应商内部文本。

## 并发和限流

- 每个 profile 新增可选 `parallel`（1–8）。未设置时继承现有全局值，最终默认 1，保持兼容。
- 整页备用路径按 solve profile 的并发值建立 semaphore；批量正常成功时不额外并发。
- token 速率窗口以“接口地址 + 模型 + API key 的不可逆哈希”为键；同一账户的不同 profile 共享预算，不同供应商不互相等待。
- 真实压测采用 1、2、3、4 个并发请求逐级测量；记录首个失败、总耗时、429、成功率及 token。只把没有 429 且成功率 100% 的最高档作为候选默认值；否则回退上一档。

## 验收

- 前端单元测试覆盖高度 clamp 与本地恢复逻辑；构建通过。
- 后端回归测试证明诊断批次两次失败时不会重复逐题解题，并会记录失败类别。
- 后端测试证明 profile 并发优先于旧全局设置，且不同供应商 token 窗口互不影响。
- GLM/DeepSeek 实测结果记录在本地、脱敏的诊断报告中；不在仓库、日志或终端输出密钥。
